Plugins declare their settings once, in their definition: `definePlugin({ settings: { defaults, registered: config } })`. The kernel builds one store per plugin registration when it plans the plugin list, so the settings exist before any document opens: `kernel.settingsOf(token)` reads and changes them with no document, and an app may set them before opening one. Inside `create`, `ctx.settings()` returns `get()` for the plugin's own code and `api`, the four settings calls to spread into the capability: `getSettings()`, `updateSettings(changes)`, `resetSettings()` and `onSettingsChanged`, which carries `{ settings, changed }`, `changed` naming the top-level settings whose value changed. The settings belong to the plugin as the app registered it, not to one document: `updateSettings()` changes every open document and the ones opened later, and wakes every reader. Changes merge the same way everywhere: plain objects merge key by key, arrays and other values replace, and `undefined` leaves a setting as it is. `resetSettings()` goes back to what the app registered, not to the plugin's defaults, and `onSettingsChanged` fires once for each call that changed a setting. The test context from `@embedpdf/core/testing` takes the same `settings` declaration. The types are exported as `Settings`, `SettingsApi`, `SettingsChangedEvent`, `SettingsDeclaration`, `SettingsOf` and `DeepPartial`.

`definePlugin` takes no type arguments: it reads the capability type from `token`, the state type from `state` and the settings type from `settings.defaults`. `create` is checked against those types, never a source of them, so a controller that returns less than the capability is a type error, and so is a controller that reads settings in a plugin whose definition declares none. A plugin without `state` is stateless (`void`); a plugin without `settings` has `NoSettings`, the default of `PluginContext`'s and `PluginDef`'s settings parameter, and `ctx.settings()` throws there. `NoSettings` is a type of its own so that one plugin list can hold plugins with and without settings.

Workspace plugins follow the document in scope. A plugin declares `inScope(api, documentId)`, the capability as seen from inside a document's scope, and resolving its token for a document (`kernel.capability(token, documentId)`, `kernel.tryCapability`, `ctx.forDocument`, or a document-scoped plugin's `ctx.get`) returns that view: the same object on every call while the document is open. Without a document, the capability itself is returned, as before. The documents capability does the same: resolved for a document, `save()`, `saveLayer()`, `listPages()`, `getPage()`, `getPageAt()`, `getPageIndex()`, `getRevision()` and `allows()` default to that document instead of the active one.
