# Building forms

The form plugin can also add fields to a PDF, and change or remove the ones it has, so people can turn
any document into a form. Switch to **design mode**, pick a field tool, and click or drag on the page:

<Snippet name="forms/field-palette" />

Building needs the [annotation plugin](../annotations) next to the form plugin: in design mode, fields
are boxes you select, move, resize and style like any annotation.

| Tool             | Places                      | A click makes |
| :--------------- | :-------------------------- | :------------ |
| `form-text`      | A text box                  | 160 × 24      |
| `form-checkbox`  | A checkbox                  | 18 × 18       |
| `form-radio`     | A radio button              | 18 × 18       |
| `form-combobox`  | A dropdown                  | 140 × 24      |
| `form-listbox`   | A list                      | 140 × 72      |
| `form-button`    | A push button               | 100 × 28      |
| `form-signature` | A field someone signs later | 160 × 48      |

A see-through preview of the field follows the pointer, drawn as the field will be, so people see
where it lands before they click. Drag instead of clicking for another size. The tool stays active, so placing ten checkboxes is ten
clicks.

## Design mode

The `form-edit` tool is design mode: fields stop being fillable and become boxes you can select, move
and resize. The `pointer` tool makes them fillable again:

```ts
interaction.activateTool('form-edit'); // design the form
interaction.activateTool('pointer'); // fill it in
```

In design mode the form lends its boxes to the annotation plugin, which selects, moves, resizes,
restyles, reorders and deletes them with its own tools, next to the annotations. Every edit of a box
is still the form's: its place or look is `updateWidget()`, and deleting every box of a field
deletes the field. A drag of two fields and a stamp is one change: one request, and one step to
undo. Like every change, it shows at once and the engine's answer follows.

A field just placed is selected at once, before the engine answers, and the tool goes back to
`form-edit` rather than the default pointer, so design mode goes on. Without `canDesign()` nothing is
lent: the fields stay fillable boxes the annotation tools leave alone.

`update()` takes only what you change, with the same settings a field reads:

| Setting                                      | What it is                                            |
| :------------------------------------------- | :---------------------------------------------------- |
| `name`                                       | Its own part of its name: renaming `customer.email` to `phone` makes `customer.phone` |
| `required`                                   | PDF apps ask for a value before the form is submitted |
| `readOnly`                                   | People can't change the value                         |
| `alternateName`                              | The tooltip, also read by screen readers              |
| `defaultValue`                               | What a reset puts back                                |
| `options`                                    | For a dropdown or list: `{ label, value }` pairs      |
| `maxLength`, `multiline`, `password`, `comb` | For a text box                                        |

`getFieldSettings(ref)` describes a field's settings for a panel you draw without knowing the
field's family: `{ properties, values }`, each property a `key` (what `update()` takes), a `control`
(`text`, `flag`, `number`, `choice`, `choices` or `options`), and a `label` in English with its
translation key, `labelKey` (`form.settings.tooltip`), in display order. A `choice`'s options are
the field's own values, shown as they are.

A field's look, such as its border, background and font, belongs to its box: change it like any
annotation's, with the [style panel](../annotations/selecting#a-style-panel), or from code with
`form.updateWidget(widget.ref, { color: '#1d4ed8' })`.

## Add fields from code

`create()` takes the same settings the engine takes, with the page and the box for each place the
field shows:

```ts
const { field } = await form.create({
  family: 'combobox',
  name: 'country',
  options: [
    { label: 'Netherlands', value: 'NL' },
    { label: 'Belgium', value: 'BE' },
  ],
  widgets: [{ page: page.ref, rect: { x: 72, y: 252, width: 148, height: 20 } }],
});
```

A radio group is one field with a box per button, each with the value it stands for:

```ts
await form.create({
  family: 'radio',
  name: 'plan',
  widgets: [
    { page: page.ref, rect: { x: 72, y: 136, width: 16, height: 16 }, exportValue: 'monthly' },
    { page: page.ref, rect: { x: 72, y: 166, width: 16, height: 16 }, exportValue: 'yearly' },
  ],
});
```

A field placed with a tool gets a name like `text_1`; rename it in your settings panel. Every
family's settings are on [Creating form fields](/docs/engine/forms/authoring).

### One more button for a group

`addWidget(ref)` shows a field in one more place: for a radio group a new choice, for a checkbox a
box that checks together with the others.

```ts
const { widget } = await form.addWidget(plan.ref);
annotation.selection.set([widget.ref]); // in design mode, so it can be dragged
```

Without a place, it goes next in line: below the last button if they stand in a column, beside it
if in a row, at the same size and the same spacing, starting a new column where the page ends. It
looks like the field's last button, and a radio group's new choice gets the next free `Choice<n>`.
Pass what you want instead: `form.addWidget(plan.ref, { rect, exportValue: 'yearly' })` takes
everything an entry of `create()`'s `widgets` takes.

## Scripts and calculations

A field's scripts go in `actions` when you create or change it: a calculated total, a formatted
amount, a check on what the user typed. The viewer runs them while the user fills the form in.

```ts
await form.update(total.ref, {
  actions: {
    calculate: {
      type: 'javascript',
      script: 'event.value = this.getField("subtotal").value * 1.21;',
    },
  },
});
await form.reorderCalculations([tax.ref], { before: total.ref });
```

A calculate script puts the field at the end of the order calculations run in;
`reorderCalculations()` moves it. Writing a script needs `canWriteScripts()`. See
[Scripts and calculations](/docs/engine/forms/authoring#scripts-and-calculations).

A box can do something when it's clicked, too, such as reset the form: give its entry of
`widgets` in `create()` its `actions`. A script, a submit or a web link there needs
`canWriteScripts()` as well. See [Widget actions](/docs/engine/forms/authoring#widget-actions).
A push button (`family: 'pushbutton'`) is a box that only does that, with a `caption`; see
[A push button](/docs/engine/forms/authoring#a-push-button).

## Remove a field

```ts
await form.delete(field.ref);
```

This removes the field and every box it has. To remove one box of a field that shows in several places,
such as a reference number on every page, use `form.deleteWidget(widget.ref)`. It resolves the field
as it is now. In design mode, deleting the selection does the same: one box goes from its field, and
a field whose every box is selected goes whole.

Every building method shows its change at once, is one step to undo, and resolves once the engine
answered.

## Methods

What `useForm()` gives you for building forms. Reading, filling and the form's state are on
[Filling forms](../forms#methods).

| Method                                  | What it does                                                                                                                                                                                          |
| :-------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create(draft)`                         | Adds a field, with a box for each place it shows. Resolves `{ field }`. [Add fields from code](#add-fields-from-code)                                                                                 |
| `update(ref, patch)`                    | Changes a field's settings; pass only what changes. Resolves `{ field }`. [Change a field's settings](#change-a-fields-settings)                                                                      |
| `addWidget(ref, placement?)`            | Shows a field in one more place: a radio group's next choice, a checkbox's next box. Resolves `{ field, widget }`. [One more button for a group](#one-more-button-for-a-group)                        |
| `delete(ref)`                           | Removes a field and every box it has. [Remove a field](#remove-a-field)                                                                                                                               |
| `updateWidget(widget, patch)`           | Changes one box's place or look; pass only what changes. Resolves `{ widget }`. [Change a field's settings](#change-a-fields-settings)                                                                |
| `getFieldSettings(ref)`                 | A field's settings described for a panel: `{ properties, values }`, or `null`. [Change a field's settings](#change-a-fields-settings)                                                                 |
| `deleteWidget(widget)`                  | Removes one box from its page, and from its field when it has one. Resolves `{ field }`, or `{ field: null }` for a box in no field. [Remove a field](#remove-a-field)                                |
| `removeWidget(ref, widget)`             | Takes one box out of its field; it stays on the page, in no field, until `deleteWidget()` removes it                                                                                                  |
| `reorderCalculations(fields, position)` | Moves fields in the order calculate scripts run in. Resolves `{ calculationOrder }`. [Scripts and calculations](#scripts-and-calculations)                                                            |
| `repair(options?)`                      | Fixes a form other PDF apps read differently, such as fields missing from the form's list, and resolves what it fixed. See [Repair a broken form](/docs/engine/forms/authoring#repair-a-broken-form). |
| `canDesign()`                           | Whether adding, changing and removing fields is allowed. [Permissions](#permissions)                                                                                                                  |
| `canRestoreAttribution()`               | Whether an import may keep who created and filled in its fields, instead of naming the importing user. [Permissions](#permissions)                                                                    |
| `canWriteScripts()`                     | Whether scripts, submit buttons and links may be written into fields and their boxes. [Permissions](#permissions)                                                                                     |

Every method that returns a promise also takes a `signal` in its options, to cancel it.

## Permissions

| Permission         | What it allows                                                  | Check                          |
| :----------------- | :-------------------------------------------------------------- | :----------------------------- |
| `doc.forms.modify` | Adding, changing, removing and repairing fields                 | `form.canDesign()`             |
| `doc.forms.import` | Importing fields and values with who created and filled them in | `form.canRestoreAttribution()` |
| `doc.forms.script` | Writing scripts, submit buttons and links into fields and boxes | `form.canWriteScripts()`       |

Hide the field tools when `canDesign()` is false, and the script, submit and link options of a
field's or a box's actions when `canWriteScripts()` is false. Scripts already in the form run either way.

## Good to know

### Fields and boxes

A field is the data: its name, its value, its settings. A **widget** is a box where the field shows on
a page. Most fields have one; a radio group has one per button, and a field can show on several pages,
all with the same value.

### Signature fields

A signature field is a place for someone to sign later. Signing it is on [Signatures](signatures).
