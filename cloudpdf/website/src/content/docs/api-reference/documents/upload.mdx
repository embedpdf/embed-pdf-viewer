# Upload a document

For TypeScript, use the high-level workflow. It hashes the source, initializes
the upload, follows the server-selected transfer path, and commits only after a
successful transfer:

```ts
import { CloudPDFClient } from '@cloudpdf/sdk';

const client = new CloudPDFClient({
  baseUrl: 'https://api.example.com',
  token: process.env.CLOUDPDF_TOKEN!,
});

const result = await client.uploads.create({
  tenantId: 'tenant_123',
  source: { path: './document.pdf' },
  idempotencyKey: 'invoice-2026-08',
  uploadPreference: 'auto',
});
```

`auto` is recommended. It uses a presigned object-store `PUT` whenever the
storage adapter supports one, so PDF bytes do not consume API-server bandwidth.
The SDK sends the returned signed headers exactly and does not attach the
CloudPDF authorization header to the object-store request.

When storage cannot presign, `init` returns `upload.kind = "proxy"`. The SDK
then sends a bounded multipart `file` to the authenticated
[`uploadProxy`](/docs/api-reference/documents/upload-proxy) endpoint. PHP and
Ruby support this path because it is standard multipart, not an untyped raw
binary request.

All generated SDKs also expose the low-level protocol:

1. Call [`documents.init`](/docs/api-reference/documents/init) with the exact
   byte length and SHA-256.
2. If the result is `presigned`, `PUT` the bytes to its URL with exactly its
   headers. If it is `proxy`, call `documents.uploadProxy` with the PDF file.
3. Call [`documents.commit`](/docs/api-reference/documents/commit) with the same
   SHA-256. A deduped init result skips both transfer and commit.

The server pins the hash, size, and selected transfer kind at init. Changing any
of them on a retry is rejected rather than silently reusing an unrelated
idempotency key.
