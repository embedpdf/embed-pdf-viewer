# How it works

CloudPDF serves PDF pages and document data over HTTP. Your backend decides
which documents a user can open and what they can do with them.

## The big picture

<ServerRequestFlow />

CloudPDF checks the JWT's signature, document ID, and permissions before serving
the request.

The bundled npm and Docker server use HS256 with `CLOUDPDF_JWT_SECRET`. To use a
public key or a JWKS URL, set `verifier` in `buildApp` in a custom Node deployment.
See [Signing modes](/docs/api-reference/authentication#signing-modes).

## The HTTP API

The [Fastify](https://fastify.dev) server exposes these routes.

| Routes | Auth | Purpose |
| --- | --- | --- |
| `/v1/docs/*` | Document JWT in the browser | Render pages, extract text, work with annotations and metadata, and unlock encrypted PDFs. |
| `/v1/tenants/*` | API token or tenant JWT with the required scope | Create documents, upload files, and manage tokens from your backend. The issue token API is available in HS256 mode. |
| `/healthz`, `/readyz` | None | Liveness and readiness probes. |

See [API authentication](/docs/api-reference/authentication) for accepted
credentials and the permissions each can carry.

## The native worker pool

PDFium is a native C++ library. The server runs it inside a pool of Node
`worker_thread`s so that CPU-heavy rendering never blocks the HTTP event loop and
several requests can render in parallel.

The pool size is controlled by
[`CLOUDPDF_WORKER_POOL_SIZE`](/docs/server/operations/health-and-scaling). The
default is conservative — `min(2, cpu count)` — and you raise it as you give the
process more cores and memory.

<Callout type="info">
  Native code parsing hostile PDFs will eventually crash. Two layers keep that
  survivable: set <code>CLOUDPDF_ENGINE_ISOLATION=host</code> so a crash costs
  a <strong>sub-second engine respawn</strong> inside the instance (documents
  that repeatedly crash the engine are quarantined automatically), and run
  <strong>multiple replicas</strong> so even an instance restart never means
  zero capacity. See
  <a href="/docs/server/operations/health-and-scaling">Health &amp; scaling</a>.
</Callout>

## Storage: database + object store

The server separates **metadata** from **bytes**:

- **Database** — document records, annotations, tokens, and the audit log. Use
  **SQLite** (a single file, zero setup) to start, or **Postgres** for
  multi-replica production. See [Database](/docs/server/configuration/database).
- **Object store** — the actual PDF bytes and rendered artifacts. Use the
  **local filesystem** for a single host, or **S3 / GCS / Azure Blob** for
  durable, shared storage. See [Storage](/docs/server/configuration/storage).
- **Cache** — a local directory of recently used documents and renders so repeat
  requests are fast. It is disposable; the server rebuilds it from the object
  store.

This split is what lets the same binary run as a zero-config single file *and* as
a horizontally-scaled cluster — you only change configuration.

<Callout type="info">
  The smallest possible setup — SQLite + local disk + local cache — needs
  <strong>no external services at all</strong>. That is exactly what the
  <a href="/docs/server/getting-started/quick-start">Quick start</a> uses.
</Callout>

## Twelve-factor by design

Everything is configured through `CLOUDPDF_*` environment variables, the
process logs to stdout, and state lives in the database, object store, and
cache — never in the container. That is what makes the same image safe to run as
one container or fifty pods.
