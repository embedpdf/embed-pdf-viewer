# Refs & identity

Pages and annotations are addressed by a **ref**: `page.ref`, `annotation.ref`. The engine hands
you refs in everything it returns, and takes them in every call that works on a page or an
annotation. You never build one; pass back the one you were given.

```ts
const { annotations } = await page.annotations.list();
await page.annotations.update(annotations[0].ref, { contents: 'Seen' });
```

This page is about what's inside a ref, for when you store one or compare two.

## Page refs

A page ref is the page's number inside the PDF file (its object number), not its position:

```ts
page.ref; // { kind: 'objectNumber', objectNumber: 12 }
```

That's why a page ref stays valid when pages move: after you move page 3 to the front, its ref
is the same, only its `index` in `doc.pages.list()` changes. A deleted page's number is never
given to another page.

When you already have a page's number (from your own database, say), `toPageRef(12)` makes the
ref. To compare two, use `pageRefsEqual(a, b)`.

## Annotation refs

An annotation ref also says which page the annotation is on. It comes in two kinds, depending on
how the annotation is stored in the file:

| Kind           | Looks like                                         |
| :------------- | :------------------------------------------------- |
| `objectNumber` | `{ kind: 'objectNumber', page, objectNumber: 48 }` |
| `baseIndex`    | `{ kind: 'baseIndex', page, baseIndex: 2 }`        |

Annotations the engine creates always get an object number. PDF files from other tools don't
always give their annotations one: an annotation stored without a number is named by the
position it has on its page in the file you uploaded, its `baseIndex`.

Both kinds name the annotation for life. Adding, moving or deleting other annotations never
changes a ref, and neither does editing the annotation itself: an annotation the file stores
without a number keeps its `baseIndex` even after the engine gives it a number of its own to
save a change. A deleted annotation's ref is never given to another annotation.

An annotation's `nm` (its name in the PDF, when it has one) is data you can read and set, like
its contents. It's not how the engine finds the annotation.

To use a ref as a key in a `Map` or an object, turn it into a string with `annotationKey(ref)`.

## Other refs

Form fields and attachments have refs too, handed out the same way:

| Thing      | Its ref          | From a name you hold              |
| :--------- | :--------------- | :-------------------------------- |
| Form field | `field.ref`      | `toFieldRef('billing.name')`      |
| Attachment | `attachment.ref` | `toAttachmentRef('figures.xlsx')` |

Use the name helpers only for a name you stored yourself; see
[Forms](/docs/engine/forms#find-a-field) and
[Attachments](/docs/engine/documents/attachments#names-and-refs).

## Storing refs

A ref is plain data: store it as JSON and pass it back later, even after the document was saved
and opened again. A ref to an annotation that no longer exists fails with `NotFound`.

## Good to know

- **Why not the current position?** Positions change whenever something is added, moved or
  deleted. A `baseIndex` is the position in the file you uploaded, which never changes, so it
  can't end up pointing at a different annotation.
- **Why not the name?** Names are optional in PDF, and other tools don't always keep them unique.
  The engine refuses to create an annotation whose `nm` is already used on its page, so names it
  writes stay unique, but it never relies on them to find an annotation.
