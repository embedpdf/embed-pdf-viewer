# Permissions

A document can be opened with less than full power: a reviewer who may comment but not download,
a signer who may only fill in the form, a public link that only shows the pages. Each thing a user
may do is a permission, a string like `doc.download`.

Check a permission before you show the control for it:

```ts
if (doc.security.allows('doc.download')) {
  showDownloadButton();
}
```

The engine checks every call too. A call the user may not make fails with `Forbidden`, so hiding
a button is about honest UI, not safety.

## Where permissions come from

<Engine local>

You give them when you open the document:

```ts
const doc = await engine.open(
  { kind: 'bytes', bytes },
  { scope: ['doc.open', 'doc.render', 'doc.text.select', 'doc.annotate.read'] },
);
```

Without `scope`, the user gets every permission, and the engine logs a reminder once. That's
handy while you build; pass the permissions your users will really have, so you see the interface
they'll see.

</Engine>

<Engine cloud>

They're in the user's token, which your backend creates. The server checks them on every request.
See [Authentication](/docs/engine/authentication#what-a-token-carries).

</Engine>

To list what the user was given (for a "you can…" panel), read `doc.security.scope`.

## Every permission

| Permission               | What it allows                                                                                             |
| :----------------------- | :--------------------------------------------------------------------------------------------------------- |
| `doc.open`               | Open the document and list its pages.                                                                      |
| `doc.render`             | Render pages as images.                                                                                    |
| `doc.text.select`        | Where text is: selecting it and the text layout.                                                           |
| `doc.text.search`        | Search, with where each match is.                                                                          |
| `doc.text.copy`          | The text itself: reading it, copying it, search snippets.                                                  |
| `doc.download`           | Download the file, attached files and stamp drawings, signed revisions; export annotations; extract pages. |
| `doc.print`              | Print, in the viewer.                                                                                      |
| `doc.pages.assemble`     | Rotate, move, delete, insert and name pages.                                                               |
| `doc.pages.modify`       | Change page content: flatten, redact (with the permissions below).                                         |
| `doc.annotate.read`      | See annotations.                                                                                           |
| `doc.annotate.modify`    | Create, change and delete any annotation.                                                                  |
| `doc.annotate.import`    | Import annotations with their original authors and dates.                                                  |
| `doc.forms.read`         | See form fields and their values.                                                                          |
| `doc.forms.fill`         | Fill in form fields.                                                                                       |
| `doc.forms.modify`       | Create, change and delete form fields.                                                                     |
| `doc.sign`               | Sign the document.                                                                                         |
| `doc.sign.certify`       | Sign as the certifying signature.                                                                          |
| `doc.metadata.modify`    | Change the title, author and other metadata.                                                               |
| `doc.attachments.modify` | Add and remove attached files.                                                                             |
| `doc.redact`             | Apply redactions.                                                                                          |
| `pdf.permissions`        | What the PDF file itself allows (its permission flags); see [below](#the-pdfs-own-restrictions).           |
| `*`                      | Everything.                                                                                                |

Some permissions include others: `doc.annotate.modify` includes `doc.annotate.read`,
`doc.forms.fill` includes `doc.forms.read`, and `doc.forms.modify` includes `doc.forms.fill` and
`doc.forms.read`. Each page of these docs says which permission its calls
need.

## Annotations

In a document many people work on, "may edit annotations" usually means "may edit _my_
annotations". Permissions for annotations can say exactly that, with the action and whose
annotations it covers:

```ts
const scope = [
  'doc.open',
  'doc.render',
  'doc.annotate.read',
  'annotations:create:self',
  'annotations:update:self',
  'annotations:delete:self',
];
```

| Part   | Values                                                                          |
| :----- | :------------------------------------------------------------------------------ |
| action | `create`, `update`, `delete`, `set-group`, or `*` for all four                  |
| whose  | `self` (the user's own), `all`, `group=<id>` (a group's), `createdBy=<user id>` |

A user's own annotations are the ones with their user id (`userId`). An `annotations:<action>:…`
permission replaces `doc.annotate.modify` for that action.
`['doc.annotate.modify', 'annotations:update:self']` lets a user create and delete any
annotation, but update only their own.

To check a single annotation before showing its edit controls:

```ts
doc.security.allowsAnnotation('create'); // may the user add annotations?
doc.security.allowsAnnotation('update', annotation); // may they change this one?
doc.security.allowsAnnotation('delete', annotation); // …delete this one?
```

## The PDF's own restrictions

A PDF can restrict itself: a file protected with an owner password may forbid printing or
copying. Add `pdf.permissions` to the scope to follow those restrictions. Without it, the engine
ignores them and only your permissions count.

<Engine local>

```ts
await engine.open(input, { scope: ['doc.open', 'doc.render', 'pdf.permissions'] });
```

</Engine>

<Engine cloud>

Put `pdf.permissions` in the token's scope, next to the other permissions.

</Engine>

When the user unlocks the file with its owner password, the file's restrictions no longer apply.
See [Opening documents](/docs/engine/documents/opening#password-protected-files).

## When a call is refused

A refused call fails with an `EngineError` whose code is `Forbidden`. It names the permission that
was missing:

```ts
import { EngineError, EngineErrorCode } from '@embedpdf/engine';

try {
  await doc.download();
} catch (error) {
  if (EngineError.is(error, EngineErrorCode.Forbidden)) {
    console.log(`missing ${error.details.required}`); // "doc.download"
  }
}
```

<Engine local>

<CloudPdfCallout
  title="Permissions that protect the file"
  href="https://www.cloudpdf.com/docs/engine/concepts/permissions"
  cta="How CloudPDF enforces permissions"
>

The local engine checks permissions in the user's browser, and the browser already has the whole
file. That keeps your interface and your code honest, but a user who takes the file out of the
page gets all of it.

With CloudPDF the file stays on your server and every call is checked there. A user without
`doc.download` never receives the file; a user without `doc.text.copy` never receives
the text; a reviewer with `annotations:update:self` can't change anyone else's comments, whatever
they send. Your code doesn't change.

</CloudPdfCallout>

</Engine>

## Good to know

### Building interface from permissions

The headless components turn permissions into one question per button, such as
`annotation.canEdit(ref)` and `selection.canCopy()`, so your interface never offers something that
will fail. See [Permissions](/docs/headless/concepts/permissions) in the headless docs.

### Groups

An annotation can belong to a group (`groupId`), for example a team or a department. New
annotations go in the user's own group. `annotations:set-group:group=<id>` lets a user move
annotations into that group; `annotations:update:group=<id>` lets them edit that group's
annotations.

### Importing with original authors

`doc.annotate.import` lets an [import](/docs/engine/annotations/import-export) write annotations
with the authors, dates and owners they had in the source document. Only give it to trusted jobs,
such as syncing from your own database: it lets the caller create annotations in someone else's
name.
