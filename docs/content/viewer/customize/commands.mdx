# Buttons & commands

Every button in the viewer runs a **command**: one action with a label, an icon, a shortcut, and
what it does. A toolbar button, a menu row and a key press all run the same command, so they always
agree. Add one of yours, then put it in the [layout](layout):

```js
{
  commands: [
    {
      id: 'acme:approve',
      label: 'Approve',
      icon: 'check',
      shortcut: 'Mod+Enter',
      run: ({ documentId }) => approve(documentId),
    },
  ],
  layout: (layout) => layout.add('acme:approve', { to: 'main', section: 'end' }),
}
```

The button's tooltip says its label and its shortcut the way the platform writes it: `Ctrl+Enter`,
or `⌘↩` on a Mac. The button moves into the "More" menu when the toolbar is full, and `Ctrl`+`Enter`
(`Cmd`+`Enter` on a Mac) runs it while the viewer has focus.

## Define a command

| Field | What it is |
| :-- | :-- |
| `id` | A unique name. Start yours with your own prefix, such as `acme:`. |
| `label` | What people see, or `labelKey` for a [translated](translations) label |
| `labelParams` | The values for its label's `{name}` slots, such as a count: see [A label with a value](#a-label-with-a-value) |
| `icon` | An icon's name: the viewer's or [your own](#icons) |
| `shortcut` | A key, such as `'Mod+Shift+S'`, or a list of keys. `Mod` is `Cmd` on a Mac and `Ctrl` elsewhere. |
| `shortcutInTextFields` | `true`: its shortcut works in a text field in the viewer too, as Find's does |
| `run` | What it does |
| `enabled` | When it can run. When it can't, its button is greyed out. |
| `active` | When it shows as pressed, or checked in a menu |
| `visible` | When it shows at all |
| `menu` | A [menu](menus) it opens, instead of `run` |
| `panel` | A [panel](panels) it opens and closes, instead of `run` |
| `requires` | The [permissions](#permissions) it needs from the scope. Without them, it's hidden. |
| `categories` | The features it belongs to, so [`features`](../features/turning-off) turns it off with them. A name of your own makes a new feature. |

A command is the same thing as in headless: see [Commands &
shortcuts](/docs/headless/ui/commands#define-a-command).

## Enabled, active and visible

`enabled`, `active` and `visible` say how a command's button looks now. They get `get`, which gives
you any plugin by its name, and `appState`, your app's own state. The viewer asks them again
whenever either changes, and after the command runs, so a button is always right:

```js
{
  id: 'acme:flag',
  label: 'Flag for review',
  icon: 'eye',
  enabled: ({ get }) => get('selection').hasSelection(),
  active: ({ appState, documentId }) => appState.flagged.includes(documentId),
  run: ({ appState, documentId }) => appState.toggleFlag(documentId),
}
```

`run` gets the same: `get`, `appState`, the `viewer`, and the `documentId` of the document it runs
for.

An `enabled`, `active` or `visible` that throws, because what it reads isn't there yet, such as a
plugin of a document while none is open, counts as `false`: the button is greyed out, not pressed,
or hidden until it answers.

### Your app's state

Give the viewer what your commands read as `appState`: values, and functions that change them. It
follows its prop like `theme` does: give it a new value, and every button asks its command again.
Here **Approve** stays greyed out until every item of the app's checklist is ticked, and shows as
pressed once the document is approved:

<Snippet name="viewer/commands/app-state" />

Because the commands read your state from `appState`, never from a variable they closed over, they
can be a constant outside your component and never see an old value. Give it a new value when
something changes, as you do with any prop: the viewer sees a new object, not a change inside the
one it has (`[...done, item]`, not `done.push(item)`). In TypeScript, `ViewerConfig<AppState>` gives
`appState` its type in every command.

## A label with a value

`labelParams` gives the values for the `{name}` slots in a label, such as how many pages are
selected:

```js
{
  commands: [
    {
      id: 'acme:extract',
      labelKey: 'acme.extract',
      label: 'Extract {count} pages',
      icon: 'download',
      labelParams: ({ get }) => ({ count: get('pageEdit').getSelected().length }),
      enabled: ({ get }) => get('pageEdit').getSelected().length > 0,
      run: extract,
    },
  ],
  strings: {
    en: { 'acme.extract': { one: 'Extract {count} page', other: 'Extract {count} pages' } },
    nl: { 'acme.extract': { one: '{count} pagina extraheren', other: "{count} pagina's extraheren" } },
  },
}
```

It gets what `enabled` gets, and the viewer asks it again whenever a plugin's state or `appState`
changes, so the label is always right. A number `count` also picks the plural form: `one` and
`other`, and the other forms a language has, such as `few` and `many` in Polish. The values go into
`label`, into the words under `labelKey` in each language, and into a string under the command's
id. The label shows with them everywhere the command does: its button, a menu, the tooltip, and the
sentence that says why it isn't allowed. A `labelParams` that throws gives no values, and the slots
show as they are.

## Change what a built-in button does

A command with a built-in id replaces the built-in one, everywhere it appears: the button, the
menu row and the shortcut. This one makes **Download** save to your server instead:

```js
{
  commands: [
    {
      id: 'document:download',
      run: async ({ viewer, documentId }) => {
        const bytes = await viewer.documents.download(documentId);
        await fetch(`/api/documents/${documentId}`, { method: 'PUT', body: bytes });
      },
    },
  ],
}
```

Give only the fields you change: the label, icon and shortcut stay the built-in ones.

## Icons

An icon is 24 × 24 SVG path data, drawn as a line, so [Tabler](https://tabler.io/icons) and
[Lucide](https://lucide.dev) icons paste in as they are. Give a name to each of yours:

```js
{
  icons: {
    send: ['M10 14L21 3', 'M21 3l-6.5 18a.5.5 0 0 1-1 0L10 14l-7-3.5a.5.5 0 0 1 0-1L21 3z'],
    logo: { paths: ['M4 4h16v16H4z'], fill: true },
  },
}
```

A string is one path, an array is several, and `{ paths, fill: true }` fills them instead of drawing
their outline. An icon with the name of a built-in one replaces it, everywhere. A command that
names an icon the viewer doesn't have logs a warning with the command's id and the icon's name.

## Permissions

A command that needs a permission from the scope says which, with `requires`. When the user
doesn't have it, the command is gone from every bar and menu, and its shortcut does nothing:

```js
{
  id: 'acme:approve',
  label: 'Approve',
  icon: 'check',
  requires: ['doc.annotate.modify'],
  run: ({ documentId }) => approve(documentId),
}
```

The names are the scope's permissions, listed on [Permissions](/docs/headless/concepts/permissions).
The built-in commands already say what they need, so for a user whose scope doesn't allow
changes the editing tools are gone, and with `notAllowed: 'disable'` they show greyed out instead,
with the reason in their tooltip. To leave a command out for everyone, turn off its feature instead:
`categories: ['acme.approve']`, then `features: { 'acme.approve': false }`. See
[Your own commands](../features/turning-off#your-own-commands).

A command whose setting a plugin [locks](/docs/headless/viewing/stage#lock-a-setting) for the
document, such as the facing-pages choices while a plugin shows one page at a time, shows greyed
out with the plugin's reason, and its current choice still checked.

## Keyboard shortcuts

A command's `shortcut` works while focus is anywhere inside the viewer, except in a text field,
unless the command says `shortcutInTextFields: true`, as Find (`search:find`, `Ctrl`/`Cmd`+`F`)
does. `?` opens a sheet with every shortcut. Your shortcut wins over a built-in one with the same
keys. Copying works the same way: `Ctrl`/`Cmd`+`C`, and Copy in the browser's Edit menu, copy the
viewer's selected text only while focus is inside it, so the page keeps its own copying.

## Run a command from code

```js
await viewer.commands.execute('zoom:fit-width');
await viewer.commands.execute('panel:search');
```

`execute()` resolves `{ status: 'executed' }`, or `{ status: 'rejected', reason }` when the command
can't run now.

## Good to know

### Tooltips

Every button in a bar, every mode tab and the buttons in a panel's header have a tooltip: the
button's label, its shortcut, and why it's greyed out when it is. A button that shows its label
already has a tooltip only when there's more to say. A greyed-out menu row says why in a tooltip
too. The tooltip shows when the pointer rests on the button for a moment, at once when the button
gets focus from the keyboard, and never from a touch. Escape hides it. Screen readers read the
shortcut and the reason with the button. Its colors are theme tokens: see
[Theming](theming#every-color).

Every other tooltip in the viewer is the same one, with the same timing: those of the buttons in
panels and dialogs, and a name too long for its row, such as an attachment's or an outline item's,
which shows whole while it's cut short.

### Enabled is for now, permissions are for good

`enabled` is for what can't run *right now*: nothing selected, nothing to undo. Its button is
greyed out, because the user can change that. What the user may never do here is a permission:
say so with `requires`, and the button isn't there at all.
