# Permissions

A document can be opened with less than full power: a link that lets people read and comment, a
signing session that only fills in fields, a reviewer who may not download. The engine refuses
everything else. This page is about building a UI that **shows only what works**, instead of buttons
that fail.

## Every verb has a check

Every call that can be refused has a check next to it, named `can` and the verb. It answers one
question: would this work right now, for this user?

```ts
annotation.canCreate(); // may they draw new annotations?
annotation.canUpdate(ref); // may they change this one?
selection.canCopy(); // may selected text leave the document?
form.canFill(); // may they fill in fields?
documents.canDownload(); // may they download the file?
```

A check already includes everything its call looks at: the user's permissions, the flags on the
document (a locked annotation, a read-only field) and what's selected. You never combine them
yourself, and you never read permission names: which permission a call needs is the plugin's
business, not yours.

> **The rule:** show a button when its check is true. Read the check while you render, like any
> other state: the answer changes when the selection changes or the user gets new permissions.

```tsx
const annotation = useAnnotation();

{annotation.canCreate() && <DrawingTools />}
<button disabled={!annotation.canDelete(ref)}>Delete</button>
```

## One answer per annotation

Checks that take a `ref` answer for that one annotation, field or comment. In a shared document, a
user may hold `annotations:update:self`: change their own annotations, and only look at the rest.
You don't handle that yourself. Someone else's annotation answers `canUpdate(ref) === false`, and
shows the way a locked one does: it can be selected and commented on, but has no handles. Forms work
the same: a field the user may not fill shows as read-only.

## Calling anyway is safe

Checks are there to keep your UI honest; the engine doesn't rely on them. A refused call rejects,
the same way in every plugin:

```ts
import { isPluginError } from '@embedpdf/react/runtime';

try {
  await form.setValue(toFieldRef('total'), { value: '120.00' });
} catch (error) {
  if (isPluginError(error, 'permission-denied')) {
    console.log(error.permission); // what was missing, such as 'doc.forms.fill'
  }
}
```

The local and the cloud engine refuse the same way, so this one check covers both.

What people do with the mouse fails quietly instead: without permission to create, drawing with a
tool paints nothing and saves nothing.

## Where the limits come from

A document gets its permissions when it opens, together with who the user is.

<Engine local>

On the local engine you give both. Once on the viewer, for every document it opens, and per document
when one needs something else:

```tsx
<Viewer
  engine={engine}
  plugins={plugins}
  identity={{ userId: 'u_381', displayName: 'Dana Smith' }}
  scope={[
    'doc.open',
    'doc.render',
    'doc.text.select',
    'doc.annotate.read',
    'annotations:create:self',
    'annotations:update:self',
    'annotations:delete:self',
  ]}
  initialDocuments={[
    { source: report },
    { source: archive, scope: ['doc.open', 'doc.render'] }, // this one is read-only
  ]}
/>
```

- **A document's own `scope` replaces the viewer's.** It's the whole list for that document, not an
  addition, so it means exactly what it says. The same goes for `identity`.
- **`identity` is who the user is.** Permissions that say "their own" (`:self`) or "their group"
  (`:group`) are checked against it, so they need one: opening without it fails.
- **A document keeps what it opened with.** Change the viewer's `scope` or `identity`, and the
  documents you open after that get the new values.

Code that opens documents itself passes the same options to
`documents.open(source, { scope, identity })`.

Leave `scope` out and the user may do everything, with a warning in the console. That's handy while
you build, but pass the scope your users will really get, so the checks show you the UI they'll see.
